# 大模型辅助迁移：经验与教训

*整理日期：2026-05-14*
*背景：基于本项目从 UrhoX Lua 引擎到 Godot 4 场景系统的迁移实践*

---

## 前言

本文档总结了在使用大模型（Claude）辅助完成游戏项目跨引擎迁移和持续重构过程中积累的经验教训。适合分享给同样在使用 AI 协作开发的团队参考。

内容不依赖具体项目，可作为通用方法论使用。

---

## 一、这次迁移做了什么

### 背景
一个卡牌+棋盘类游戏，最初完整实现于 UrhoX 引擎（Lua 脚本），后期决定将 UI 层迁移至 Godot 4，保留 Lua 的游戏逻辑层。

### 主要迁移内容
- **逻辑层**（保留 Lua）：卡牌系统、事件系统、剧情系统、对话系统
- **表现层**（迁移 Godot）：主菜单、设置页面、棋盘 UI、对话框、商店弹窗
- **资产管线**：AI 图片生成工作流、音效管理

### 工作流特点
- 全程使用大模型（Claude）作为主要编码助手
- 通过 Skill 机制将重复任务固化为可复用的"操作手册"
- 采用双分支策略：`main`（Lua 逻辑）和 `godot_scene_dev`（Godot 场景）

---

## 二、有效的做法

### 2.1 用 Skill 文件固化重复性工作流

**做法**：每当一类任务需要重复操作时，将操作步骤写成 `SKILL.md`，后续直接引用。

**本项目中的例子**：
- `card-image-generation` — 图片 AI 生成的提示词规范、命名格式、存放路径
- `card-image-integration` — 图片生成后如何更新 `CardImageMap.lua`
- `godot-scene-refactor` — Godot `.tscn` 文件的生成规范和节点命名约定

**为什么有效**：
1. 大模型没有"记忆"——上一轮对话的决策在下一轮默认不存在
2. Skill 文件相当于把"上次谈好的结论"持久化到文件系统里
3. 后续每次开始相关任务，只需要说"按照 xxx skill 来做"，不需要重新解释背景

**教训**：如果你发现自己在不同对话里反复向 AI 解释同一个约定，那这个约定就应该写成 Skill 文件。

---

### 2.2 先写设计草稿，再让 AI 实现

**做法**：在 `docs/` 目录下维护设计草稿文档（如 `mid_day_events_draft.md`），先用文档描述系统设计，再让 AI 根据文档生成代码。

**为什么有效**：
1. 文档是对话的"锚点"——AI 可以反复引用，不会偏离设计意图
2. 草稿阶段发现设计问题比代码阶段成本低得多
3. 文档本身就是需求规格，让 AI 实现时边界更清晰

**教训**：不要直接说"帮我做一个白天事件系统"，要先说"白天事件系统应该有这些：[枚举列表]，然后帮我实现"。

---

### 2.3 明确的提交信息策略

**做法**：提交信息包含 scope 标签，区分迁移目标：
- `feat(main):` — Lua 逻辑层新功能
- `feat(godot):` — Godot 场景新功能
- `refactor(godot):` — Godot 场景重构
- `merge(main→godot_scene_dev):` — 分支合并，明确策略

**为什么有效**：
1. 大模型理解提交历史时，scope 能快速定位"这是哪个系统的改动"
2. 合并提交的说明（"lua脚本以main为准，godot以本地为准"）避免了反复解释合并策略
3. 方便人类和 AI 协作时快速对齐上下文

**教训**：迁移项目中，提交信息要比普通项目更精确地标注"影响范围"。

---

### 2.4 资产命名规范文档化

**做法**：在 `image-generation-style-guide.md` 中定义文件命名格式：
```
{类型}_{标识符}_{时间戳}.png
```

**为什么有效**：
1. 大量 AI 生成图片时，统一命名让 `CardImageMap.lua` 的维护变得机械化
2. 时间戳后缀解决了同一资产多版本共存的问题（不删旧版，方便回滚）
3. 命名本身携带语义（`loc_`/`evt_`/`npc_` 前缀），AI 能自动推断资产类型

**教训**：资产命名规范要在项目早期就定好并文档化，中途改变命名规范代价极高。

---

### 2.5 双向分离的架构决策

**做法**：Lua 处理游戏逻辑，Godot 处理 UI 呈现，通过数据接口解耦。

**为什么有效**：
1. AI 在专注单一系统时产出质量更高（不需要同时理解两套引擎的 API）
2. 每次 PR/合并有明确的"以哪边为准"的决策依据
3. 两套系统可以独立演进，互不干扰

**教训**：如果让 AI 同时维护两套高度耦合的系统，上下文很容易混乱，导致错误的跨系统引用。

---

### 2.6 AI 图片资产批量生成流水线

**做法**：建立一套固定的图片生成流水线：风格指南文档 → 标准化 prompt 模板 → AI 生成 → 按命名规范存档 → 代码集成。每张图都走同一条路径，不需要临时决策。

**本项目中的例子**：在整个迁移周期内，通过这条流水线生成了 50+ 张素材（地点卡图、事件插图、NPC 立绘、道具图标），每次操作步骤相同，没有一张需要返工重做：
1. 查 `image-generation-style-guide.md` 确认风格关键词和尺寸
2. 填写 prompt 模板（类型前缀 + 内容描述 + 风格词）
3. 调用 AI 生成工具，目标尺寸和透明背景由模板决定
4. 生成文件自动带时间戳落地，无需手动重命名
5. 更新 `CardImageMap.lua` 或 `CardImageMap.gd` 中的映射表

**为什么能直接完成**：
1. 流水线的每一步都有明确的输入和输出，没有模糊决策点
2. 命名规范把"这张图是什么"编码进文件名，集成步骤变成机械操作
3. 风格指南保证了批量生成的视觉一致性，不需要反复对齐风格

**教训**：一旦这条流水线跑通，后续每一张图的边际成本极低。但如果前期没有文档化风格指南，每次生成都要重新描述风格，成本会线性增长。

---

### 2.7 结构清晰的 Lua → GDScript 直接迁移

**做法**：当 Lua 代码有清晰的分层设计（数据层/状态机/渲染层分离）时，可以让 AI 做几乎 1:1 的结构映射迁移，不需要重新设计。

**本项目中的例子**：对话系统（`DialogueSystem.lua` → `dialogue_system.gd`）的迁移几乎没有返工：
- Lua 版本有明确的状态机（`idle → entering → typing → waiting → exiting`）
- 动画属性和数据属性已经分离（data class 模式）
- 公开 API 边界清晰（`start()` / `handle_click()` / `on_enter_complete()`）

AI 迁移时只需要做语法转换（`local` → `var`、`function` → `func`、`:` → `.`），状态机逻辑和接口设计直接保留，迁移后可立即使用。

**为什么能直接完成**：
1. 结构良好的原始代码让 AI 不需要做架构决策，只需做语法翻译
2. 状态机模式在 Lua 和 GDScript 中几乎等价，没有语义损失
3. 迁移范围明确（一个文件对一个文件），不涉及跨系统重构

**操作要点**：
- 迁移前先问 AI "这段代码的主要职责是什么、输入输出是什么"——如果 AI 能清晰回答，说明代码结构足够清晰，可以直接迁移
- 如果 AI 的回答含糊，说明原始代码需要先整理再迁移

---

### 2.8 "识别模式 → 扩展实现 → 接线" 三步新功能开发

**做法**：实现新功能时，先找到代码库中结构最相似的已有功能，以它为模板直接扩展，最后在所有触发点接线。

**本项目中的例子**：实现"裂隙卡牌上显示 chibi 图标"功能，全程无调试循环：
1. **识别模式**：发现已有怪物幽灵 chibi 系统（`_mg_create_sprite()` + `_mg_card_nodes` + `_process` 浮动动画）
2. **扩展实现**：新增 `_rift_card_nodes`、`rift_show_on_card()`、`rift_clear_all()`，逻辑与 monster ghost 完全对称，只换了贴图路径和颜色（紫色脉冲）
3. **接线**：在 `card_interaction.gd` 中所有 `_show_rift_confirm()` 调用前插入 `rift_show_on_card()`，共 5 处，一次完成

从开始到完成没有中间的"运行 → 发现 bug → 修 → 运行"循环。

**为什么能直接完成**：
1. 已有模式经过测试，扩展它比从零设计出错率低
2. 接线点有限且可穷举（搜索所有 `_show_rift_confirm()` 调用即可定位），没有遗漏风险
3. AI 在有明确参照时产出质量显著高于开放式需求

**操作要点**：
- 开始前明确说"参考 xxx 的实现方式"，而不是"实现一个类似 xxx 的功能"——前者给 AI 代码参照，后者让 AI 自由发挥
- 接线完成后，搜索一遍所有同类触发点，确认没有遗漏

---

### 2.9 先读代码识别架构，再定修复方案（补救型）

**做法**：在修复 UI 问题前，先让 AI 分别阅读 `.tscn` 和对应的 `.gd` 文件，明确"谁负责什么"，再决定改哪里。

**本项目中的例子**：用户问"商店 UI 是 Scene 还是纯代码绘制？"——AI 同时读取了 `shop_popup.tscn`（面板骨架）和 `shop_popup_scene.gd`（`_draw_cards()` 逻辑），得出"混合架构"的结论：Scene 提供容器节点，`_draw()` 负责卡牌渲染。这直接决定了布局 bug 的修复策略（改 `.tscn` 的 `custom_minimum_size`，而不是改代码里的常量）。

**为什么有效**：
1. 混合架构下，单看其中一个文件会产生误判——Scene 里看不到实际渲染尺寸，代码里看不到容器约束
2. 明确职责边界后，AI 的修改不会"改错地方"
3. 对 AI 来说，"先读再改"的指令非常明确，产出稳定

**操作要点**：
- 遇到 UI/布局问题时，先问"这个组件的 Scene 文件和脚本文件分别是什么"
- 让 AI 描述清楚架构分层后，再说"现在帮我修复 xxx"

---

### 2.10 先全量诊断，再批量修复（补救型）

**做法**：用户一次性报告多个 bug 时，先逐一定位所有 bug 的根本原因，汇总成清单，再按顺序统一修复；而不是"修一个、测一个"地串行迭代。

**本项目中的例子**：用户一次提交了 5 个 bug（商店布局、立绘层级、步数负数、步数异常、剧情后卡死）。AI 先逐一追溯根因，发现它们分属 4 个不同文件的独立问题，相互之间无依赖关系，然后再一次性完成全部修复。

**为什么有效**：
1. 多个 bug 分散在不同文件时，并发分析比串行效率高得多
2. 先摸清全貌，可以判断 bug 之间有无因果关系，避免"修 A 破 B"
3. 一次上下文加载多个文件，比多轮对话反复加载更节省 token

**根因诊断的通用流程**：
```
1. 复现路径：什么操作触发、在哪个状态下
2. 代码追溯：沿调用链找到异常分支
3. 确认范围：是单点问题还是系统性问题
4. 评估依赖：各 bug 的修复之间是否有顺序要求
5. 统一修复
```

**操作要点**：
- 报告 bug 时尽量附上 log 或截图，根因定位速度可提升数倍
- 鼓励 AI 先说"我找到了 N 个根因，分别是……"再动手修改，不要边分析边改

## 三、踩过的坑

### 3.1 "上下文遗忘"导致决策漂移

**问题描述**：在一次对话中确定了某个数据结构设计，几轮对话后 AI 生成的代码开始偏离原始设计，使用了不同的字段名或不一致的接口。

**根本原因**：大模型没有跨会话记忆，即使在同一个长对话中，早期信息也会被"稀释"。

**解决方案**：
- 关键的数据结构/接口定义必须写入文件（如 Skill 文件或专门的 `design-spec.md`）
- 每次涉及已有接口时，主动让 AI "先读对应文件再写代码"
- 重要决策写入提交信息，让 git log 成为决策记录

---

### 3.2 迁移时的"幻觉路径"

**问题描述**：让 AI 将 Lua 代码迁移为 Godot GDScript 时，AI 有时会生成看起来正确但实际无法运行的代码——尤其是 `res://` 路径引用、节点路径 `$NodeName` 等 Godot 特有的语法细节。

**根本原因**：大模型对 Godot 4 的了解基于训练数据，可能混入了 Godot 3 的旧语法，或者对项目实际的节点树结构一无所知。

**解决方案**：
- 在 `godot-scene-refactor` Skill 中明确规定 Godot 4 语法要点（GDScript 2.0、`$` 符号、信号连接方式）
- 对 Godot 场景文件，要求 AI 先阅读现有 `.tscn` 文件了解节点结构，再生成引用代码
- 建立"可运行验证"步骤：每次生成 Godot 代码后在编辑器里实际跑一遍

---

### 3.3 Skill 文件重叠与冲突

**问题描述**：本项目有两个功能重叠的 Skill：`mid-day-events` 和 `midday-events`，内容略有差异，导致 AI 偶尔引用了错误的版本。

**根本原因**：Skill 文件在迭代过程中没有做版本管理，新版本直接新建而不是替换旧版本。

**解决方案**：
- Skill 文件命名要唯一，迭代时直接修改原文件，不要复制新建
- 如果确实需要多个版本，在文件内部用版本号标记，并明确标注"当前推荐版本"
- 定期审查 `.claude/skills/` 目录，删除或归档过时的 Skill

---

### 3.4 资产路径的两套系统冲突

**问题描述**：UrhoX 资产路径不需要 `assets/` 前缀（引擎自动处理），而 Godot 需要完整的 `res://assets/` 路径。AI 有时会在 Godot GDScript 中使用 UrhoX 风格的路径。

**根本原因**：两套引擎的资源系统约定不同，AI 在上下文切换时容易混淆。

**解决方案**：
- 在 `godot-scene-refactor` Skill 中专门说明路径差异
- 建立"路径速查表"写入 Skill 文件：
  ```
  UrhoX Lua:  "Textures/player.png"        # 相对于资源根
  Godot GDS:  "res://assets/image/xxx.png" # 完整资源路径
  ```
- 每次涉及路径的代码生成，都要求 AI 先确认当前是在哪个引擎上下文中

---

### 3.5 初始化调用链遗漏

**问题描述**：游戏第一天步数显示为 `-19/0`（负数），而第二天以后完全正常。

**根本原因**：`reset_daily_steps()` 在"重新开始游戏"和"新的一天开始"路径中都有调用，但在"首次从标题画面进入游戏"的路径（`_on_title_start()`）中遗漏了调用。因为大模型在实现各个入口时，并不会自动"全局扫描"所有调用路径，只会实现当前提到的那条路径。

**症状特征**：只在游戏首次启动时复现，reload/重开后消失——这类 bug 容易被测试流程遗漏。

**解决方案**：
- 对于"每天/每局开始时必须执行的初始化"，主动梳理所有入口路径并列成清单：
  ```
  重置步数的入口：
  ✅ 重新开始游戏 (restart_game)
  ✅ 新的一天开始 (_begin_new_day)
  ❌ 首次从标题进入 (_on_title_start) ← 容易遗漏
  ```
- 向 AI 描述功能时，说清楚"所有需要调用的地方"，而不是只说一个入口

---

### 3.6 _draw() 绘制顺序即 Z 轴层级

**问题描述**：对话界面中立绘（角色立图）显示在对话框的前面（上方），遮挡了对话文本。期望效果是立绘在对话框后面，只有上半身露出。

**根本原因**：在 Godot 的 `_draw()` 中，后调用的 `draw_*` 语句渲染层级更高（覆盖前面的内容）。AI 在迁移 Lua 的"分层绘制"逻辑时，没有注意到 Lua 原版中立绘绘制于对话框背景之前，而迁移后把立绘 `draw_texture_rect` 放到了函数末尾。

**症状特征**：UI 层级问题不会报错，只能靠肉眼观察，容易被延迟发现。

**解决方案**：
- 向 AI 交代 `_draw()` 代码时，明确标注各元素的"期望层级顺序"：
  ```
  绘制顺序（从后到前）：
  1. 遮罩背景
  2. 立绘          ← 对话框之前
  3. 对话框背景
  4. 对话框文本
  5. 选项按钮
  ```
- `_draw()` 迁移后要进行视觉验收，检查每个 UI 元素的层叠关系

---

### 3.7 过渡状态（Transit State）的恢复陷阱

**问题描述**：玩家翻开一张卡片时触发了剧情对话，剧情结束后游戏卡死，玩家无法再操作任何卡牌。

**根本原因**：对话系统在进入对话前保存了 `demo_state = "flipping"`（翻牌中），对话结束时原样恢复，但 `"flipping"` 是一个过渡态——这个状态的正常结束由翻牌流程负责，一旦被"意外恢复"就再也不会退出，游戏卡死。

**症状特征**：只在特定时机触发（翻牌期间产生对话），正常流程中不复现。

**解决方案**：
- 所有保存/恢复状态的逻辑，都要区分"稳定状态"和"过渡状态"：
  ```gdscript
  # 过渡状态列表（不应被恢复）
  const TRANSIT_STATES = ["flipping", "dealing", "moving"]
  
  # 恢复前检查
  var restore = _prev_state if _prev_state not in TRANSIT_STATES else "ready"
  GameData.set_demo_state(restore)
  ```
- 向 AI 描述"保存并恢复状态"的需求时，要同时说明哪些状态是过渡态、遇到时应该 fallback 到哪里
- 过渡态触发的分支（如"翻牌中触发事件"）要单独作为测试用例覆盖

---

### 3.8 Scene 尺寸与代码渲染尺寸脱节

**问题描述**：商店弹窗打开后内容物（3 张商品卡）溢出面板，或面板过小只显示了一小块区域。

**根本原因**：`.tscn` 文件中写死了 `custom_minimum_size = Vector2(310, 260)`，而实际渲染代码（`_draw_cards()`）中卡牌总宽为 3×234 + 2×42 = **786px**，两者相差近 2.5 倍。AI 在生成 `.tscn` 时使用了一个"看起来合理的"占位数值，没有反查代码中的实际尺寸常量。

**症状特征**：在 Godot 编辑器预览时布局可能看起来正常（因为编辑器不执行 `_draw`），只有运行时才发现问题。

**解决方案**：
- 混合架构（Scene 骨架 + `_draw()` 绘制内容）时，**Scene 的尺寸常量要从代码常量反推**：
  ```
  CARD_W=234, CARD_H=330, CARD_COUNT=3, CARD_GAP=42
  → 最小宽度 = 3×234 + 2×42 + panel_padding×2 = 786 + 48 ≈ 840px
  → 最小高度 = 330 + padding ≈ 340px
  ```
- 生成 `.tscn` 时，要求 AI 先阅读对应的 `_draw()` 代码，确认实际渲染尺寸
- 每次修改卡牌尺寸相关常量，同步更新 `.tscn` 中的 `custom_minimum_size`

---

### 3.9 分支策略不清晰导致合并混乱

**问题描述**：在 `godot_scene_dev` 分支上修改 Lua 文件后，合并回 `main` 时产生了冲突，需要人工判断以哪边为准。

**根本原因**：双分支策略需要有明确的"文件归属"规则，否则每次合并都要重新决策。

**解决方案**：
- 明确文件归属规则并写入项目文档：
  - `scripts/*.lua` → 以 `main` 分支为权威
  - `godot/**` → 以 `godot_scene_dev` 为权威
  - `assets/` → 两边共享，新增文件不产生冲突
- 在合并提交信息中明确说明策略（如 "lua脚本以main为准，godot以本地为准"）
- 考虑用 `.gitattributes` 的 merge strategy 来自动化部分决策

## 四、关于 Skill 机制的深度反思

### Skill 的本质是什么？

Skill 文件解决的是大模型的一个核心局限：**它没有项目记忆，但你可以把"记忆"写成文件**。

一个好的 Skill 文件应该回答：
1. **什么时候用**（触发条件）
2. **做什么**（操作步骤）
3. **注意什么**（坑和约定）
4. **产物是什么**（期望输出）

### Skill 文件的生命周期

```
需求出现
  → 手动完成一次，积累经验
  → 第二次遇到时，边做边整理成草稿
  → 第三次遇到时，从草稿提炼为正式 Skill
  → 持续迭代，发现不对的地方就修改
  → 任务消失后，归档或删除
```

### Skill 文件不适合做什么

- **不适合**记录"一次性"的决策（这类放提交信息或 ADR 文档）
- **不适合**取代代码注释（代码本身的意图还是要在代码里解释）
- **不适合**过度细化——太长的 Skill 文件 AI 反而容易忽略关键部分

## 五、给大模型辅助迁移的操作建议

### 启动迁移前
- [ ] 写一份"迁移范围文档"，明确哪些东西迁移、哪些保留、哪些重写
- [ ] 定义文件归属规则，写入文档
- [ ] 建立资产命名规范，写入 Skill 文件
- [ ] 设置 commit message 的 scope 约定

### 进行中
- [ ] 每完成一类重复任务后，问自己"这个流程以后还会用吗？"——如果是，写 Skill
- [ ] 每次让 AI 读取相关文件后再写代码，不要依赖其"记忆"
- [ ] 对跨系统引用（如 Lua 调 Godot 接口）保持警惕，要求 AI 先确认接口定义
- [ ] 实现新功能时，主动列出该功能的所有调用入口，防止某条路径遗漏初始化（见 3.5）
- [ ] `_draw()` 代码迁移后必须进行视觉验收，重点检查各 UI 元素的层叠顺序（见 3.6）
- [ ] 使用"保存/恢复状态"模式时，同步告知 AI 哪些是过渡态及其 fallback 目标（见 3.7）
- [ ] 混合架构（Scene + `_draw()`）中修改尺寸常量后，同步更新 `.tscn` 的 `custom_minimum_size`（见 3.8）

### 定期维护
- [ ] 每周审查一次 `skills/` 目录，删除或合并重叠的 Skill
- [ ] 当系统接口发生变化时，第一时间更新对应的 Skill 文件
- [ ] 定期让 AI "读取所有 Skill 并指出可能的矛盾"

## 六、一句话总结

> **大模型辅助迁移的核心技巧是：把所有决策显式化。**
>
> 凡是你在脑子里记住的"约定"，都应该写成文件。
> 大模型不会忘记文件里的内容，但它会忘记你上次说的话。
